# قواعد تطوير نظام الإيجارات (Flutter Web + PHP + MySQL)

## عقد العمل والقواعد النهائية للمشروع

من الآن وحتى انتهاء المشروع، نلتزم بالقواعد التالية دون استثناء:

### 1. عدم التنفيذ المباشر
قبل أي تعديل، يجب تنفيذ المراحل التالية بالتسلسل:
1. **Discovery (الاستكشاف)**
2. **Validation (التحقق)**
3. **Impact Analysis (تحليل الأثر)**
4. **Execution Plan (خطة التنفيذ)**

ولا يبدأ التنفيذ إلا بعد موافقة المستخدم الصريحة.

### 2. معايير إغلاق المهام
لا تعتبر أي مهمة منتهية إلا بعد:
* تنفيذ التعديل.
* مراجعة الكود.
* اختبار الوظيفة كاملة.
* قياس الأداء قبل وبعد.
* تحديث التوثيق ذي الصلة.
* كتابة تقرير مختصر بالنتائج.

### 3. التقرير الثابت لكل مرحلة
عند كل مرحلة، يجب تقديم تقرير بالهيكل والتنسيق التالي:
1. **المهمة الحالية**
2. **الهدف**
3. **الملفات التي سيتم تعديلها**
4. **سبب التعديل**
5. **المخاطر**
6. **خطة التنفيذ**
7. **خطة التراجع (Rollback)**
8. **طريقة الاختبار**
9. **معايير النجاح**
10. **النتيجة بعد التنفيذ**

### 4. قاعدة التقدم التدريجي
لا يُسمح بتعديل أكثر من 3 ملفات في المرحلة الواحدة إلا بعد الحصول على موافقة صريحة من المستخدم.

### 5. تحليل الأثر (Impact Analysis)
قبل تعديل أي ملف، يجب التحقق من:
* هل يوجد ملف آخر يعتمد عليه؟
* هل سيؤثر على Flutter؟
* هل سيؤثر على PHP؟
* هل سيؤثر على قاعدة البيانات؟
* هل سيؤثر على العملاء الحاليين؟
* هل سيؤثر على التوافق بين V1 و V2؟

ويجب إرفاق هذا التحليل بشكل واضح قبل أي طلب موافقة.

### 6. تعديلات قاعدة البيانات
قبل أي تعديل في قاعدة البيانات:
* تحقق من إصدار قاعدة البيانات الحالي.
* تحقق من توافقها مع الكود البرمجي الحالي.
* تحقق من وجود نسخة احتياطية (Backup).
* تأكد من وجود خطة تراجع (Rollback).
* يمنع تماماً استخدام `ensure_*_schema` داخل الطلبات التشغيلية (Runtime HTTP Requests).
* يجب استخدام نظام الهجرة وتتبع الإصدارات (Migration Versioning) فقط.

### 7. دقة البيانات والقياسات
يمنع تقديم أرقام تقديرية على أنها قياسات حقيقية. إذا ذكرنا أي من التالي:
* زمن الاستجابة (Response Time / TTFB).
* عدد الاستعلامات (SQL Query Count).
* حجم البيانات (Data/Response Size).
* استهلاك الذاكرة والمعالج (Memory/CPU Usage).
* عدد الطلبات (Requests Count).

فيجب توضيح مصدرها بدقة (مثال: DevTools، سجلات خادم Apache/PHP، إحصائيات MySQL، قياس فعلي، إلخ)، أو التنويه بوضوح أنه تقدير يحتاج إلى تحقق.

### 8. كفاية المعلومات وعدم التخمين
إذا لم تكن المعلومات المتوفرة كافية، يمنع التخمين تماماً. يجب طلب الملفات، السجلات (Logs)، أو بنية قاعدة البيانات المطلوبة أولاً.

### 9. توثيق المشاكل المكتشفة
عند اكتشاف أي مشكلة أثناء العمل، تُعرض بالتنسيق التالي:
* **الوصف**: شرح المشكلة.
* **السبب**: ما الذي أدى للمشكلة.
* **الدليل**: الكود أو السجل الذي يثبت وجودها.
* **الملف والسطر**: موقع المشكلة بدقة.
* **مستوى الخطورة**: (منخفض / متوسط / حرج).
* **الحلول الممكنة**: الخيارات المتاحة.
* **الحل الموصى به**: الحل الأفضل ولماذا.
* **الأثر المتوقع**: أثر الحل على الأداء والعملاء.
* **طريقة الاختبار**: كيف سنتأكد من نجاح الإصلاح.

### 10. جدول إغلاق المرحلة
عند نهاية كل مرحلة، يجب تقديم جدول يحتوي على التقييم التالي:

| البند | الحالة |
|---|---|
| **التنفيذ** | ✅ / ❌ |
| **الاختبارات** | ✅ / ❌ |
| **قياس الأداء** | ✅ / ❌ |
| **التوافق مع V1** | ✅ / ❌ |
| **التوافق مع V2** | ✅ / ❌ |
| **Rollback** | ✅ / ❌ |
| **التوثيق** | ✅ / ❌ |

### 11. سجل المشروع (PROJECT_STATUS.md)
إنشاء وتحديث ملف باسم `PROJECT_STATUS.md` في مجلد المشروع الرئيسي باستمرار ليتضمن:
* المرحلة الحالية.
* المهام المنجزة.
* المهام المتبقية.
* المشاكل المفتوحة.
* القرارات المعتمدة.
* آخر قياسات الأداء.
* سجل التعديلات.
* الإصدار الحالي وحالة توافق قاعدة البيانات.

ويتم تحديث هذا الملف بعد كل مرحلة لضمان عدم فقدان السياق عند استئناف العمل.

### 13. قاعدة التنفيذ الذهبية (Golden Rule)
قبل أي تعديل يلتزم المطور/الوكيل بالبنود الثابتة التالية:
* عدم تعديل Business Logic.
* عدم إعادة هيكلة الكود (No Refactoring).
* عدم تغيير أسماء الدوال أو الـ APIs.
* عدم تعديل قاعدة البيانات (No DB Schema changes).
* عدم تعديل Models.
* عدم تعديل Providers أو Controllers إلا إذا كانت المشكلة ناتجة منها مباشرة.
* أي تعديل يجب أن يكون Minimal & Isolated (أقل تعديل ممكن ومستقل).
* إجراء اختبار Regression بعد كل مرحلة للتأكد من أن الوظائف غير المتأثرة ما زالت تعمل كما كانت.

### 14. معايير قبول المرحلة (Acceptance Criteria)
عند نهاية كل مرحلة، يجب التحقق من استيفاء جميع الشروط التالية:
* لا تتغير أي وظيفة حالية خارج نطاق المهمة.
* جميع الاختبارات الخاصة بالمهمة تنجح.
* لا تظهر أخطاء جديدة في السجلات (Logs).
* اجتياز اختبار Regression قبل الانتقال للمرحلة التالية.
